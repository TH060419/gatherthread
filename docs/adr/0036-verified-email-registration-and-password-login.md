# ADR-0036: Verified email registration and password login

**Date**: 2026-09-30
**Status**: proposed / unreleased source preview
**Deciders**: pending project-lead review

## Decision

Add optional email registration alongside qualification activation and project invitations. Email is the login account identifier; the user verifies an eight-digit OTP, chooses a password, and receives a normal qualified account. It has exactly the same project creation, roles and deployment resource quotas as a qualification-code account. Registration creates no project, runtime or model allocation. Future hosted Agent entitlement must be an independent, server-enforced quota and must not treat one verified address as one unique person. Registration never merges, upgrades or binds existing qualification/invitation identities. Existing device-token and remembered-account login remain compatible.

Registration remains closed by default. Opening requires HTTPS, persistent credential pepper, an approved mail sender and mandatory server-verified Turnstile. Missing dependencies and challenge failures close registration. A persistent local circuit breaker stops sends and completion without disabling existing email/password login. No network administrator endpoint, mock-mail environment setting or automatically purchased service is added.

Use an OTP rather than a verification link to keep capabilities out of URLs, referrers and browser history. OTPs expire in ten minutes, allow five attempts, and bind the initiating HttpOnly browser marker. Resend has a 60-second cooldown and invalidates all earlier codes for that email. Idempotent send retries within the ten-minute record lifetime return the same receipt without resending; changed email/locale conflicts. Failed or uncertain delivery consumes the budget and invalidates the OTP. A crash before delivery acknowledgement requires a later fresh resend, never automatic delivery retry.

Passwords use Node's stable scrypt API with a random 16-byte salt and a versioned hash, N=131072, r=8, p=1. Only one expensive hash runs per process, with no unauthenticated queue. OTP validation reserves a private verification proof in a short write transaction, hashing runs outside SQLite, then completion rechecks proof, expiry, pause, unique email and account budget. Account, email digest, password hash, device, browser binding, session and OTP consumption commit together. Interrupted hash/verification requires a fresh code. Login does equivalent hash work for unknown addresses; it returns a uniform invalid-credentials error and persists IP/browser/email/global budgets before expensive work. Its completion rechecks the account hash after async work to fence deletion.

Email/password login issues an opaque HttpOnly session for a browser-specific device, reusing that browser's unrevoked device. A different browser gets a distinct device. Neither new endpoint returns a device token; the user need not record one. Explicit Remember uses the existing vault and 30-day session; ordinary sessions retain 24-hour absolute expiry. Old token login and connector/device authorization remain available. Password recovery, email changes, adding email/password to an existing qualification account and account merging are excluded pending separate recovery and reauthentication designs. Forgotten-password limitation is visible in both languages.

## Alternatives and cost evidence (checked 2026-09-30)

- **Resend REST adapter, recommended provisional sender**: official [pricing](https://resend.com/pricing) lists 100/day on Free, SMTP/REST support, 30-day provider retention and no SLA on Free. Its [free-tier announcement](https://resend.com/blog/new-free-tier) states 3,000/month. Domain verification/DKIM, provider approval and actual current account quota are operator prerequisites. Do not enable Transactional Overages or auto-upgrade. Our shared key must not serve unrelated workloads without subtracting their budget. REST supports an idempotency key and needs no new dependency; the mailer interface allows a reviewed SMTP adapter later.
- **Brevo REST/SMTP, viable alternative**: [official Free-plan limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan) give 300/day without rollover; up to 1,000 excess transactional emails may queue for retry. Queued verification mail can arrive after OTP expiry, so delivery behavior needs operator evaluation and a separate adapter. Do not assume unlimited sending or guaranteed inbox placement.
- **Self-hosted SMTP**: avoids a paid API only if trusted mail infrastructure already exists. DNS authentication, sender reputation, port policy, bounce management and operator effort remain costs. No public relay or direct SMTP implementation is used as a zero-cost shortcut.
- **Turnstile**: official [plans](https://developers.cloudflare.com/turnstile/plans/) include a Free plan for applications independent of Cloudflare proxying. [Server validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/) is mandatory; tokens expire after five minutes and are single use. We check success, exact configured hostname, `gt_register` action and browser-bound cdata, and persist local replay protection. Follow the [Privacy Addendum](https://www.cloudflare.com/turnstile-privacy-policy/) and [supported browsers](https://developers.cloudflare.com/turnstile/reference/supported-browsers/). Blocked script/verification has an accessible error/retry/back path and cannot bypass the challenge.

No official material establishes reliable delivery to QQ/163/Outlook/SJTU recipients or challenge accessibility from mainland mobile networks for this deployment. Provider uptime statements are not inbox guarantees. Approved test inboxes on those networks, bounce/spam checks and sender setup are mandatory before opening. This PR sends no real mail, creates no provider account and accepts no terms.

## Persistence and compatibility

Additive strict tables preserve all existing users/devices/cookies/roles/events: `public_registration_accounts`, `email_login_devices`, `registration_pending`, `registration_budgets`, `registration_control`, `registration_deleted_emails`. Mailbox policy supports conventional ASCII, case-insensitive addresses only; lowercase and trim, preserving dots and plus suffixes. Case-sensitive/Unicode mailbox use is unsupported rather than silently merged. The service retains keyed email digests instead of plaintext addresses because recovery/change is not implemented. Digests are pseudonymous personal data, not anonymization.

Deployment/user data limits remain the existing Alpha quotas. New registration budgets bound account creation and mail cost, not project permissions. Retention, limits, proxy prerequisites and rollback are owned by [SECURITY](../SECURITY.md), [INTERFACE_CONTRACTS](../INTERFACE_CONTRACTS.md) and [OPERATIONS](../OPERATIONS.md). The sender and challenge are dependency-injected in isolated tests; no production mock fallback exists.

## Threat and rollout boundary

Knowing an email alone cannot bind an old account, create a session, reset a password, revoke devices or gain a role. Registration is still vulnerable to humans or bots controlling many mailboxes; aggregate signup and future model budgets are necessary. Distributed attempts, account lockout DoS, IPv6 churn, provider outages and inbox delays remain operational concerns. Review actual edge/header/log/backup settings before enablement. Official [MIIT filing rules](https://www.miit.gov.cn/gyhxxhb/jgsj/cyzcyfgs/bmgz/xxtxl/art/2024/art_84a0cfa0ebd049bbbe751dca9a008e56.html) require accurate filing information and changes; the existing invitation-only filing is not evidence that publicly opened registration or later hosted model services satisfy all requirements. Confirm applicability with the access provider and competent authority, including personal-data processing and provider transfer disclosures, before rollout.
