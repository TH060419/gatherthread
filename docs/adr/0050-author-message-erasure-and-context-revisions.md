# ADR-0050: Author message erasure and deletion-aware execution revisions

- Status: proposed / implementation review
- Date: 2026-10-12
- Related: [0008](0008-local-agent-conversations-as-rebuildable-projections.md), [0026](0026-native-first-context-management.md), [0027](0027-shared-manual-history-summaries.md), [0038](0038-isolated-hosted-trial-agent.md), [0039](0039-cloud-github-repository-tasks.md), [0045](0045-streamed-public-agent-output.md)

## Context

Hiding a message in the browser does not remove it from a replay page, a summary, a frozen import, a provider prompt or an already compacted local Agent conversation. A user needs to delete their own shared message without giving the project owner permission to delete another member's message, without leaving gaps in canonical order, and without deleting local workspaces or native tasks.

## Decision

### Transactional erasure, not an alternate readable copy

The browser-only deletion endpoint rechecks its active device, allowed Origin, test admission where enabled, current session write permission and exact message author inside `BEGIN IMMEDIATE`. Eligible targets are human chat, Agent request and the author's Agent answer. The project owner has no override. Deleting an answer does not delete its preceding request. Deleting a request also erases its linked public progress, tools, answer and failure. The mutation is idempotent for one actor, target and key; key reuse with different authority or target conflicts.

Deleting a final answer also erases that same request's generated progress, answer streams and tool outputs, which can retain copies produced before the final message. Its earliest still-readable associated output becomes the boundary for invalidating later snapshots and generated answers. Earlier independent answers, the original human question and independently authored human chat/requests remain; an Agent-generated copy based on an earlier streamed answer is not independent human content.

Deletion replaces live SQL payload/provenance with a safe placeholder, records an authoritative deleted index and increments the session's `content_revision`. Immutable event ID, sequence, type, author, timestamp and reply reference remain. The server appends one payload-free `message_deleted` control event. Clients cannot forge that event through generic append or local-turn upload. Keyed identity-bound input receipts permit an exact original append retry to return the current tombstone without retaining the original body or restoring it. Changed retries conflict. Account deletion detaches deletion-receipt author links just as it detaches retained shared-event attribution.

Canonical order and envelopes stay append-only. Explicit author erasure is the deliberate exception to immutable content. HTTP, WebSocket, MCP, mentions, quote lookup, frozen-head replay and native import all read that same scrubbed authority; selecting an older `through_sequence` cannot restore old bodies. A control receipt lists at most 256 affected IDs, with an explicit truncation flag. Every client must refresh authoritative replay from zero, whether or not that list is truncated; the list is an accelerator, not proof that all dependent caches were cleared.

### Derived summaries and answers cannot resurrect a source

Summary dependencies expand recursively. A summary citing deleted content, including one citing an earlier summary, is invalidated; valid uncovered originals return to the folded context. Old context snapshots are also invalidated. Since an Agent answer can restate any earlier input without declaring its exact sources, generated answers/work whose request followed the deleted source are conservatively invalidated. This includes content generated by another member's Agent, but does not delete that member's independent human chat or ordinary request. Public reasons distinguish author deletion from request/summary-derived invalidation. Quotes remain references; their independently authored text is not rewritten into or out of a copied source body.

### Every execution pins the current content revision

An accepted request and its claimed execution pin the history revision that produced their context. All model dispatch, progress, completion, native uploads, frozen imports, cloud code checkpoints, private GitHub task caches, continuation and PR publication recheck that pin against SQLite authority. A code checkpoint and a private task cache mutation check under their own write lock, not only before an asynchronous operation. Existing exact claim/profile, account-device, repository-consent and private API configuration fences remain independent and must all hold.

Personal API revisions fence new model work and continuation; changing a config never silently supplies its new credentials to an old request. As in [ADR-0049](0049-account-owned-cloud-api-configuration.md), reviewing or publishing an already completed private GitHub result invokes no model and does not require that old API configuration to remain enabled. Its history and GitHub authorization fences still apply. Erasing shared history invalidates that private result, so neither review, continuation nor publication can use it. Requester-private retry selection and hosted same-key retries reject an erased request or stale history pin; this does not alter exact canonical append retries returning a tombstone. New requests cannot quote an erased source.

Native, cloud and GitHub requests send their originally captured `content_revision` as a private control input, including ordinary new requests and automatic retries/resumes. The acceptance transaction rejects a changed revision before allocating an event, task, budget, slot or start interval. Omission is compatible only in a pristine revision-zero session; after any deletion, missing pins fail closed with `context_changed` and a refresh instruction. This also closes the old-page race where deletion occurs after a client-side source/selection check but before an unpinned retry arrives. MCP exposes and strictly forwards that captured pin rather than fetching a current revision for an already prepared body; ordinary human chat remains unchanged, and exact same-key canonical tombstone retries stay safe. A rejected automatic retry never silently refreshes its pin or falls back to another payer/model. Web source/revision rechecks after each asynchronous step provide earlier refusal, not the authoritative lock. Source-ID summary requests contain no cached source body: the server captures the current revision before acceptance, and the transaction independently validates/rebuilds the selected sources and digest while checking that pin.

A deletion invalidates older active session executions. Same-process notification accelerates cancellation, while an independent authority probe and transactional final checks remain decisive after reconnect, process restart or another database handle's mutation. The server records a safe `context_changed` failure rather than accepting stale progress/finals. No automatic rerun, model switch or extra charge is initiated. Already accepted provider use remains in its budget ledger. A cloud resource slot remains occupied until the executor actually exits; cancellation intent is not proof of released capacity. Already-issued provider/remote calls cannot be recalled, but no subsequent authorized dispatch or publication may start with the old pin.

### Clean native projections instead of reusing compacted memory

Connectors read deletion-aware context for every request, even when no summary is currently selected. Codex fingerprints include content revision, context policy and valid summary identity; DSH owns a fresh execution Session after a revision change. An old GT-owned native projection is permanently `local_only`, so Hooks, discovery, manual upload, polling and durable outboxes cannot republish it. A replacement must be rebuilt and verified from surviving canonical content before the binding switches. Old tasks, local history and workspace files remain intact. Failed rebuilding refuses execution; it does not fall back to the old compacted conversation.

Only fully adapted runtimes advertise `context_deletion_version: 1`. A legacy connector remains usable for a session that has never erased content. After deletion it receives `409 connector_update_required` for execution or new uploads, with a user-facing update/reconnect instruction. Giving an old journal a new revision is not adaptation.

### Storage retention is a separate boundary

The live SQL body and derived private caches are scrubbed immediately. SQLite `secure_delete=ON` is enabled before updates, and pending live-file cleanup records a durable generation. Startup and the one-minute maintenance loop attempt transaction-free `wal_checkpoint(TRUNCATE)` without waiting on other readers; a blocked cleanup stays pending, including after restart. A newer deletion cannot be acknowledged by an older cleanup generation. A pending cleanup reaching 14 days raises a fixed, content-free private operator warning and requires intervention before the retention deadline. This is not an online VACUUM or arbitrary filesystem deletion job.

This prevents a false claim of instant physical erasure: WAL, filesystem snapshots, storage-controller copies and backups are not erased by merely changing a row. Routine backup and unreachable cloud Git retention remain at most 14 days, and logs containing user identifiers at most 30 days, under the existing operator policy. A restore must reapply the latest erasure records before serving traffic. Operators must resolve blocked WAL cleanup and enforce their offline-copy policy; the application does not certify a stopped host's retention or erase independent copies.

## Consequences and verification

- Native rebuilding may produce a new local task; retaining the previous task is deliberate, not an unlearning promise.
- Conservative derived invalidation can remove an otherwise useful generated answer. Surviving human history remains authoritative and can be summarized again in a new explicit request.
- Deletion does not retract an already submitted provider request, erase manually copied text, delete local files/tasks or remove an already published GitHub copy.
- Protocol migration preserves sequence, foreign keys and exact retry behavior. Tests use two SQLite handles and concurrent workers, reopen/migration, old frozen heads, revoked/viewer/Solo/foreign actors, nested summaries/quotes/mentions/MCP, active progress/final/checkpoint races, cloud private-cache/publication races, held executor slots and next written prompt sentinels. Native adapters separately verify replacement/compaction/reconnect behavior.
- Release review must exercise both this history revision fence and any private API configuration revision fence on the integrated main branch. Unit success is not evidence of live provider, production deployment or native GUI validation.

SQLite maintenance behavior follows the [official secure-delete and WAL-checkpoint documentation](https://www.sqlite.org/pragma.html#pragma_secure_delete); ordinary-table erasure does not certify external storage or backup copies.
