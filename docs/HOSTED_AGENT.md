# Hosted trial Agent

The hosted trial Agent runs [OpenCode](https://github.com/anomalyco/opencode) in a fresh container for each request. OpenCode provides code reading, editing, terminal commands, and local tests. GatherThread keeps the provider credential on the server and exposes only a short-lived, quota-capped model proxy over a Unix socket. The container has no general network interface.

This feature is off by default. When enabled, **Cloud Agent** appears beside Codex and DeepSeek Harness in the project Agent selector. Choose its model there or in **Settings → Default Agent**, then use the existing **Request my agent** action. Existing local selections are preserved. No local connection is required; model credentials and pool capacity are operator settings, not browser settings. GT Cloud code is read only when the user selects **Use GT Cloud code and save changes to my GT Cloud branch**. The project owner must already have enabled GT Cloud file sharing. On success, changed source is checkpointed to the requesting member's own GT Cloud branch; the owner review and merge boundary remains unchanged. The runner does not read GitHub code from the direct local GitHub integration. Without the selection, the Agent works in an empty, disposable project directory and file changes are discarded.

The current Web entry is held for a later release: its checkbox and run actions remain disabled even when the server has configured endpoints. It is not selected automatically and does not count toward the required usable Agent in Settings. A legacy cloud-only preference retains its unavailable composer target and offers Codex in Settings, without silently rerouting a request. After that entry is released, the cloud model and status settings appear only while **Cloud Agent** is checked in **Available Agents**, independently of which Agent is the default. Unchecking it hides all cloud-specific settings. GitHub connection and saved-task review remain in the existing **Cloud Git → GitHub** category.

Model profiles are an operator-configured list, not automatically discovered or compatibility-certified by the status endpoint. Before activation, verify each exact API key, HTTPS base URL and model ID with a real tool-call round trip and multi-turn coding run. Keys stay in the private server environment. OpenCode supports project `SKILL.md` discovery, but this preview has no GT skill configuration UI or verified hosted skill-loading workflow; those capabilities are not claimed as complete.

For the separate GitHub + npm development workflow, see [Cloud GitHub tasks](HOSTED_GITHUB.md). It requires its own GitHub App authorization and activation gate; the limits below describe the GT Cloud trial.

## Operator setup

Deploy this preview on a Linux host with Docker and Unix socket support. Windows hosts reject the enabled configuration; the container smoke test is exercised on Linux CI.

1. Build `ops/hosted-agent/Dockerfile` in a reviewed build pipeline or on the deployment host with `docker build -f ops/hosted-agent/Dockerfile -t gt-hosted:reviewed .` and record its immutable local image ID with `docker image inspect --format '{{.Id}}' gt-hosted:reviewed`. Alternatively use a registry image reference pinned as `repository@sha256:<digest>`. The image pins OpenCode 1.18.32 and includes Node.js, Git, and socat. Run an isolated smoke test of `opencode run`, code editing, terminal commands, Unix-socket model access, and container cleanup before setting the feature flag.
2. Select a tool-calling Chat Completions provider. The proxy supports Cloudflare Workers AI, DeepSeek, and operator-configured HTTPS OpenAI-compatible endpoints. Each provider/model requires a live compatibility test before activation. Gemini's native API and Responses-only APIs are not supported by this adapter.
3. Set `GATHERTHREAD_HOSTED_AGENT_ENABLED=true`, `GATHERTHREAD_HOSTED_AGENT_IMAGE=sha256:<local-image-id>` (or `repository@sha256:<registry-digest>`), and `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` in the private server environment. The JSON example below references secret environment variable **names**, never literal keys.
4. Set `GATHERTHREAD_HOSTED_AGENT_MAX_CONCURRENT` (default 2, maximum 8), `GATHERTHREAD_HOSTED_AGENT_USER_MAX_CONCURRENT` (default 1, no greater than host capacity), and `GATHERTHREAD_HOSTED_AGENT_USER_MIN_INTERVAL_SECONDS` (default 30, range 1–3600). These gates apply to accepted task starts across both trial and GitHub tasks, all models, devices, projects and sessions belonging to one user. They do not count individual tool/model calls within a task. Increasing API capacity also requires enough host memory and CPU: every concurrent trial container is capped at 768 MiB and one CPU; repository tasks use 2 GiB and two CPUs.

## Selected free-model setup

The first selected provider is SiliconFlow with exactly `Qwen/Qwen3.5-4B` and `Qwen/Qwen3-8B`. The official [price page](https://siliconflow.cn/pricing) listed both at zero input/output prices on 2026-10-03. These are integration candidates, not provider-tested models. Copy the inactive [environment template](../ops/hosted-agent/siliconflow-free.env.example) into the private server configuration. Prepare a real-name verified account and `GATHERTHREAD_SILICONFLOW_API_KEY`; keep the key out of chat, source, browser storage and screenshots. Configure the reviewed image digest, reconfirm zero pricing, and run real tool-call/coding and deployment-host tests before activation. Public third-party service eligibility must also be confirmed against the provider's account terms.

`GATHERTHREAD_HOSTED_AGENT_PRESET=siliconflow-free` creates two public model choices (`sf-qwen35-4b`, `sf-qwen3-8b`) through the existing HTTPS Chat Completions adapter. Both share one account capacity group. A preset and `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` cannot be combined. Adding a different model requires an explicit operator configuration; there is no paid fallback.

This preset has **no daily task-count allowance** for users or the deployment by default. Each user may run one task at a time, with at least 30 seconds between accepted starts; the host/account initially permits two simultaneous tasks across users. The provider's own RPM/TPM limits, 429 cooldown, and the existing per-task tool-call, context, memory and timeout bounds still apply. These controls do not promise unlimited parallel capacity or a fixed inference speed. Browser settings reuse the existing model/status fields and omit “runs left today” when the user daily limit is absent.

The general provider setup retains `GATHERTHREAD_HOSTED_AGENT_USER_DAILY_RUNS` (default 1) and `GATHERTHREAD_HOSTED_AGENT_GLOBAL_DAILY_RUNS` (default 4). The explicit value `none` disables a default daily limit only when **all** endpoints are the two confirmed zero-price SiliconFlow models with `daily_runs: null`. Other providers/models retain numeric account and user/global ceilings. Explicit per-user administrator limits remain effective, including `hosted-agent:set-user-limit --user-id ID --runs 0` to deny one user. Remove old daily-run/Neuron environment overrides when switching to the free preset; administrator overrides remain effective. If prices or provider eligibility change, stop the free service and review configuration before accepting more tasks.

## Multiple APIs and accounts

Example `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` value (put actual `DEEPSEEK_A` and `DEEPSEEK_B` secrets only in the private environment):

```json
[
  { "id": "ds-a", "profile_id": "coding", "label": "DeepSeek coding", "provider": "deepseek", "model": "deepseek-chat", "token_env": "DEEPSEEK_A", "quota_group": "account-a", "daily_runs": 20, "max_concurrent": 1 },
  { "id": "ds-b", "profile_id": "coding", "label": "DeepSeek coding", "provider": "deepseek", "model": "deepseek-chat", "token_env": "DEEPSEEK_B", "quota_group": "account-b", "daily_runs": 20, "max_concurrent": 1 }
]
```

Replace the example model with a model actually available on the accounts. Up to 32 endpoints may be configured. Entries under one `profile_id` must have the exact same provider, model and display label. A different provider/model needs its own profile and an explicit user selection. The scheduler reserves one available account with the fewest active runs, then the fewest daily reservations. There is no waiting queue or automatic provider/model fallback. If upstream returns 429, 401/403 or 5xx, that account enters a short in-memory cooldown for subsequent tasks; the accepted run is not replayed automatically on another account.

All keys belonging to the same billed account or organization **must use the same `quota_group`**, daily limit (including `null`) and concurrency limit. Shared groups count usage across models. Use only legitimately provisioned capacity in accordance with provider terms; multiple keys on one account do not create extra quota. Group IDs must stay stable across restarts/configuration changes or accounting cannot associate previous usage. The operator is responsible for mapping non-Cloudflare credentials to their real accounts. Browser status exposes only model choices, availability, user rate limits and any configured daily allowance, never account IDs, endpoints or secrets.

For a custom provider use `provider: "openai-compatible"`, `base_url: "https://api.example.com/v1"`, an explicit model and quota group. URLs must be HTTPS without embedded credentials or query parameters. Streaming tool-call compatibility must be tested with the real service.

Cloudflare entries use `provider: "cloudflare-workers-ai"`, `model: "@cf/qwen/qwen3-30b-a3b-fp8"`, `account_id`, `free_plan_confirmed: true`, and at most four daily runs. Their quota group is derived from the account ID, so multiple keys cannot multiply the account allowance. The legacy single-Cloudflare environment variables remain supported when no endpoint JSON is configured: `GATHERTHREAD_HOSTED_AGENT_FREE_PLAN_CONFIRMED`, `GATHERTHREAD_CLOUDFLARE_ACCOUNT_ID`, `GATHERTHREAD_CLOUDFLARE_AI_TOKEN`. Old `*_DAILY_NEURONS` values convert to whole runs by dividing by 2000; new run variables take precedence.

Every run reserves its user cooldown, user/account/host slot and any configured daily allowance transactionally before its canonical request is created. A failed accepted task still consumes its start interval and any daily allowance. Rejected requests consume neither a slot nor an interval; exact idempotent replay never consumes another reservation. Trial proxies cap eight calls, 64,000 bytes per request and 1024 output tokens per call; [repository tasks](HOSTED_GITHUB.md) have separate bounded allowances. Cloudflare additionally keeps the conservative 2000-Neuron per-run ceiling and cannot run repository tasks. Other providers use bounded runs, **not invoice-accurate token/currency accounting**: set a provider-side spend cap for paid models and monitor the actual bill. A successful idempotent replay never launches another container.

The container runs without general network access, host credentials, or writable host directories. Its working directory is a bounded in-memory filesystem; the host supplies only read-only initial code. It is non-root, read-only except for bounded temporary storage, and has CPU, memory, PID, and wall-time limits. A user's code can run terminal commands **inside that container**, so do not mount the Docker socket, server database, deployment files, SSH agent, or host home into it. OpenCode permissions are convenience controls inside the container and are not the isolation boundary.

## Current limits

The preview accepts at most 100 project files and 500 KiB of code, at most 12 KiB of shared conversation context, and a two-minute run. Package downloads and arbitrary web access are unavailable from the container. Commands using dependencies already present in the image or source workspace can run; a project that needs external packages must use a separately approved dependency strategy. New files that exceed the cloud code rules are not checkpointed. These limits keep the trial service bounded; they are not a claim that every project can build inside this runner.

The operator must validate the container path on its deployment host before enabling the flag. Unit tests use a mocked Docker runner and model response; they do not prove that OpenCode can complete a real provider-backed project task. No billable provider request is made by the test suite.

For provider alternatives and the exact operator handoff, see [model API options](HOSTED_AGENT_PROVIDERS.md).

## Upgrade compatibility

The free-profile status contract uses `null` for absent daily limits and adds optional `rate_limits` plus `user_busy` / `rate_limit` availability states. Deploy the matching server and Web assets together; earlier preview clients cannot interpret unlimited daily status. Numeric quotas keep their previous meaning, and administrator `--runs 0` still disables a user. The additive `hosted_agent_user_activity` and `hosted_agent_active_runs` tables backfill existing reservations idempotently, retain cooldown after session/project deletion and keep an active slot until completion or single-process startup recovery. User activity has one row per account, and active slots are bounded by host capacity. Account deletion removes user activity and nulls the active slot's user link; the minimal request ID, quota group and start time remain only until its executor settles. Completion releases the slot even when task, session or account rows no longer exist. A failed Docker exit check retains its slot until operator recovery; model sockets and temporary source are still cleaned. Startup stops and verifies all interrupted `gt-hosted-*` / `gt-repository-*` containers on the dedicated Docker host before releasing reservations; cleanup failure prevents startup. The atomic migration from cascading active slots preserves every extant reservation and its indexes. It cannot reconstruct slots already removed by an earlier preview. Downgrading this preview loses the new rate-control guarantees and requires stopping all runners first.

`hosted_agent_daily_usage` separately retains only the request ID, user ID, UTC day and quota group for each accepted reservation. It has no event/session/project/account foreign key: deleting cloud history, a saved task or an account does not refund that day's user/global/account consumption. Completed, failed and interrupted tasks count alike; exact retry does not create another charge. Startup atomically backfills retained current/legacy jobs with `INSERT OR IGNORE`; restarting or recovering interrupted slots leaves current-day charges intact. Startup and subsequent accepted reservations remove older UTC days. No deleted message body, source, device ID or provider credential is retained in this ledger. Reservations deleted before this migration cannot be reconstructed; the migration cannot recover their past usage. Downgrading to a preview that counts only retained jobs loses this guarantee and is unsupported.

Deploy server and Web assets together. The status response now advertises profiles and run counts instead of the earlier preview's single fixed model and Neuron counters. Old requests without `profile_id` use `default` only if that profile exists. Old accepted requests whose payload omitted the profile must not be silently reinterpreted; conflicting reuse returns 409. Browser settings v13 supports the cloud choice while preserving the active local harness and its settings; neither defaults nor migration enable the held cloud entry.

Already accepted jobs can settle after their timeline fills or a storage cap is lowered. A model answer must still fit ordinary storage quotas; otherwise only a fixed charged failure is retained. The private terminal control allowance and confirmed-exit release rule are specified in [Security](SECURITY.md#persistence-and-redaction-requirements). Recovery never retries model execution automatically.

SQLite upgrade retains the original preview tables and copies existing reservations, IDs and user limits into `hosted_agent_runs` / `hosted_agent_run_limits` idempotently. Earlier reservations with no account metadata count conservatively against every account for that UTC day. Stop the old process and back up the database before upgrading. Downgrading to the old single-provider runner after accepting pooled runs would undercount usage and is unsupported; restore a pre-upgrade backup only with explicit data-loss review. This is a single active server-process design, not a distributed worker scheduler.
