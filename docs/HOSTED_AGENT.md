# Hosted trial Agent

The hosted trial Agent runs [OpenCode](https://github.com/anomalyco/opencode) in a fresh container for each request. OpenCode provides code reading, editing, terminal commands, and local tests. GatherThread keeps the provider credential on the server and exposes only a short-lived, quota-capped model proxy over a Unix socket. The container has no general network interface.

Beta 1 opens the **Cloud Agent** Web entry beside Codex and DeepSeek Harness; the server runner remains off by default. After the operator has configured and validated it, choose its model in the project selector or **Settings → Default Agent**, then use the existing **Request my agent** action. Local Codex remains the default, and existing local selections are preserved. No local connection is required; model credentials and pool capacity are operator settings, not browser settings. GT Cloud code is read only when the user selects **Use GT Cloud code and save changes to my GT Cloud branch**. The project owner must already have enabled GT Cloud file sharing. On success, changed source is checkpointed to the requesting member's own GT Cloud branch; the owner review and merge boundary remains unchanged. The runner does not read GitHub code from the direct local GitHub integration. Without the selection, the Agent works in an empty, disposable project directory and file changes are discarded.

The reviewed Beta 1 Web entry uses `CLOUD_AGENT_ENTRY_ENABLED=true`. Actual service availability still requires `GATHERTHREAD_HOSTED_AGENT_ENABLED`, a configured exact provider/model, a digest-pinned image and deployment-host verification. Missing capacity/configuration fails explicitly; selecting Cloud Agent never silently runs a local Agent or another model. Cloud model/status settings appear only while **Cloud Agent** is checked in **Available Agents**, independently of the default Agent. Unchecking it hides those settings. The separately configured GitHub repository-task path uses `GATHERTHREAD_HOSTED_GITHUB_ENABLED`, its own GitHub App and the eligible coding profile; account connection and saved-task review remain in **Cloud Git → GitHub**. Both Web task entries are open in Beta 1, but no API key, GitHub App configuration or live acceptance is supplied by opening the UI. This release authorizes the test service only, not production activation.

The cloud trial supports shared selected-history summaries and author-only Pause/Resume on the same composer button, without a connected local Agent. Accepted requests return immediately; final results arrive through canonical replay. Resume starts a new exact-profile request, not a lossless continuation. Cloud repository tasks retain their separate task lifecycle. See [ADR-0042](adr/0042-cloud-request-lifecycle-and-selected-summaries.md).

Model profiles are an operator-configured list, not automatically discovered or compatibility-certified by the status endpoint. Before activation, verify each exact API key, HTTPS base URL and model ID with a real tool-call round trip and multi-turn coding run. Keys stay in the private server environment. OpenCode supports project `SKILL.md` discovery, but this preview has no GT skill configuration UI or verified hosted skill-loading workflow; those capabilities are not claimed as complete.

For the separate GitHub + npm development workflow, see [Cloud GitHub tasks](HOSTED_GITHUB.md). It requires its own GitHub App authorization and activation gate; the limits below describe the GT Cloud trial.

## Operator setup

Deploy this preview on a Linux host with Docker and Unix socket support. Windows hosts reject the enabled configuration; the container smoke test is exercised on Linux CI.

1. Build `ops/hosted-agent/Dockerfile` in a reviewed build pipeline or on the deployment host with `docker build -f ops/hosted-agent/Dockerfile -t gt-hosted:reviewed .` and record its immutable local image ID with `docker image inspect --format '{{.Id}}' gt-hosted:reviewed`. Alternatively use a registry image reference pinned as `repository@sha256:<digest>`. The image pins OpenCode 1.18.32 and includes Node.js, Git, and socat. Run an isolated smoke test of the loopback OpenCode session API, code editing, terminal commands, Unix-socket model access, final-answer collection and container cleanup before setting the feature flag.
2. Select a tool-calling Chat Completions provider. The proxy supports Cloudflare Workers AI, DeepSeek, and operator-configured HTTPS OpenAI-compatible endpoints. Each provider/model requires a live compatibility test before activation. Gemini's native API and Responses-only APIs are not supported by this adapter.
3. Set `GATHERTHREAD_HOSTED_AGENT_ENABLED=true`, `GATHERTHREAD_HOSTED_AGENT_IMAGE=sha256:<local-image-id>` (or `repository@sha256:<registry-digest>`), and `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` in the private server environment. The JSON example below references secret environment variable **names**, never literal keys.
4. Set `GATHERTHREAD_HOSTED_AGENT_MAX_CONCURRENT` (default 2, maximum 8), `GATHERTHREAD_HOSTED_AGENT_USER_MAX_CONCURRENT` (default 1, no greater than host capacity), and `GATHERTHREAD_HOSTED_AGENT_USER_MIN_INTERVAL_SECONDS` (default 30, range 1–3600). These gates apply to accepted task starts across both trial and GitHub tasks, all models, devices, projects and sessions belonging to one user. They do not count individual tool/model calls within a task. The default memory policy is `limited`: `GATHERTHREAD_HOSTED_AGENT_MEMORY_MIB` defaults to 768 and permits 256–768 MiB; `GATHERTHREAD_HOSTED_GITHUB_MEMORY_MIB` defaults to 2048 and permits 256–2048 MiB. Both require integers. In limited mode RAM and combined RAM/swap caps are equal, so a task cannot spill into host swap. The default CFS quota remains one CPU for trial and two for repository tasks. The explicit [single-CPU compatibility mode](#single-cpu-cpuset-compatibility) uses a different hard CPU-range bound. Operators may tighten those limited-mode caps; a reduced limit can cause an explicit failed task, not an automatic retry or resource increase. Removing RAM/swap caps requires the separate explicit [shared-host policy](#shared-host-memory).

### Single-CPU cpuset compatibility

On a Linux host where `cpu` is unavailable in cgroup v2 but `cpuset`, `memory` and `pids` are available, an operator may choose `GATHERTHREAD_HOSTED_AGENT_CPUSET=<one online logical CPU index>`. The value must be a canonical decimal index from 0 to 4095, with no ranges, lists or whitespace; host concurrency must explicitly be one. Omission retains the original `--cpus` quota path. This is never an automatic fallback after a Docker error.

This mode passes `--cpuset-cpus` instead of `--cpus` and forces the new resource-checking image entrypoint. A previous image without that entrypoint refuses the run. Before loading OpenCode or contacting a model, the guard resolves the process's actual unified cgroup and requires exactly the selected effective CPU and a finite PID cap no larger than trial 128 or repository 256. In the default `limited` memory policy it also requires a finite memory cap no larger than requested and zero swap. The explicit [shared-host policy](#shared-host-memory) has different memory checks. Missing, wider or malformed controls fail without starting Agent work. Rebuild and record a reviewed immutable image digest; do not patch installed JavaScript, replace Docker with a flag-stripping wrapper or reuse an unchecked image.

The **Isolated test candidate** workflow accepts one fixed main commit and supplies separate verified application and image artifacts from that exact Git-less build. `scripts/test-environment/export-hosted-image.sh` builds the image once, runs provider-free trial and repository checks in both CPU modes plus shared-host guarded checks on the same immutable image ID, and produces a bounded archive, checksum and public build provenance. Only after all checks succeed are the three application files and three image files uploaded as separate Actions artifacts for three days; the public repository's artifacts contain public source/dependencies and build identity only. No registry publication or automatic deployment occurs. Pre-merge artifacts are marked `reviewed_main: false` and must never be installed as reviewed main. Use matching exact-source/run artifacts together, not a later rebuild or mutable tag. CI verifies container behavior, not the deployment host's aggregate isolation or real model compatibility.

The operator must additionally place the application, dedicated rootless user manager, daemon and **all container scopes** below a system-administrator-owned common ancestor with the chosen memory policy, the existing aggregate PID budget and the same singleton `AllowedCPUs`. Restricting only `docker.service` misses sibling container scopes. The delegated user must not be able to change or escape the ancestor's controls. Check `cpuset.cpus.effective`, not only unit text; monitor CPU hotplug/configuration changes. On a shared two-CPU test host, leave another online CPU outside the runner's range, without changing production or host security services.

This limits CPU execution width to one logical CPU, which can remain fully busy. It is **not** a fractional CFS quota, CPU fairness guarantee or an exclusive reserved core. PID/time limits, model gates and cleanup remain unchanged; memory/swap follow the explicitly chosen policy, never an automatic fallback. An in-container check does not prove the host daemon's aggregate controls. Before activation, a small provider-free fixture must confirm daemon/container membership in the common ancestor, that extra threads cannot expand their CPU range, actual container and ancestor limits, and cleanup. See [ADR-0040](adr/0040-explicit-single-cpu-hosted-compatibility.md).

### Shared-host memory

An administrator may explicitly set `GATHERTHREAD_HOSTED_AGENT_MEMORY_POLICY=shared-host`, `GATHERTHREAD_HOSTED_AGENT_MAX_CONCURRENT=1` and an exact `GATHERTHREAD_HOSTED_AGENT_CPUSET` to let trial and repository tasks use host RAM and swap on demand through the Linux guarded entrypoint. No memory is reserved for an idle test or production service. The runners omit Docker's `--memory` and `--memory-swap`; numeric `*_MEMORY_MIB` settings remain validated but apply only to `limited`, which is the unchanged default. Unknown policies, an absent cpuset or concurrency greater than one are refused. This is a deployment setting, not a browser or per-request permission.

The matching rebuilt cpuset image requires its own `memory.max`, `memory.high` and `memory.swap.max` to be `max`, while still checking the selected CPU and finite PID cap. The administrator must independently inspect **every actual ancestor** of the application, user manager, daemon and container scopes. An old finite `MemoryMax`, `MemoryHigh` or `MemorySwapMax=0` higher in that tree still constrains the work even if the leaf says `max`. Make the reviewed persistent and runtime controls agree and retain their root ownership and rollback copy; do not confuse a similarly named empty slice with the effective hierarchy.

This policy deliberately gives up memory containment and can slow or OOM-kill other services on a shared host. Use it only with explicit acceptance of that tradeoff. It does not change CPU/PID/time gates, network isolation, non-root/read-only filesystems, provider selection, quotas, credentials, or project permissions. OS memory management, not a preallocated test-service quota, governs actual consumption. A real completed provider answer and confirmed container cleanup are required to establish that a live startup problem is fixed; health checks or a low overall memory percentage alone do not establish the cause. See [ADR-0043](adr/0043-explicit-shared-host-memory.md).

### Isolated test-host activation

Keep `GATHERTHREAD_HOSTED_AGENT_ENABLED=false` until the test host passes this sequence, then enable it only in `/etc/gatherthread-test/gatherthread.env`. For GitHub repository tasks, independently validate the [App setup and repository runner](HOSTED_GITHUB.md#operator-setup) before setting `GATHERTHREAD_HOSTED_GITHUB_ENABLED=true`. Never copy production provider/GitHub credentials, user source or environment files into test.

1. Record a reviewed image digest and the actual Docker endpoint/authorization used by the service UID. Prefer a security-reviewed rootless Docker deployment or constrained runner authorization. Set `DOCKER_HOST` to that daemon's absolute local Unix socket (the default is `unix:///var/run/docker.sock`); remote daemons, Docker contexts/TLS and operator-supplied `DOCKER_CONFIG` are refused. Detection, execution and cleanup use the same socket and a fresh private empty CLI configuration, without inherited provider secrets, proxies or credential helpers. Do not expose the Docker API, make its socket world-writable, or casually add the collaboration service to a root-equivalent Docker group. Check rootless resource-limit support and the user mapping for read-only source mounts and model/dependency sockets.
2. Preserve the hardened systemd service, including `PrivateTmp=true`. Its private `/tmp` is not automatically visible to the Docker daemon, so Docker bind sources created there can fail even when a root-shell smoke passes. Create a service-owned, restricted host-visible temporary parent such as `/var/lib/gatherthread-test/hosted-tmp` and set `TMPDIR=/var/lib/gatherthread-test/hosted-tmp` in the private test environment. Confirm it is covered by the unit's existing permitted writable paths and visible to the reviewed daemon. Do not disable the sandbox or mount the host home, database or Docker socket into task containers to solve this problem.
3. Run the actual image/container/socket/source-mount/cleanup smoke under the complete test systemd service UID and sandbox. A test run as root outside the service is insufficient. Verify that a model request uses only the host proxy and that credentials never enter the container, response, screenshot or log. Test startup interrupted-container cleanup using the same Docker authorization.
4. The private Beta 1 test template starts with host and per-user concurrency 1, the existing 30-second interval, **512 MiB for trial tasks and 768 MiB for repository tasks**. A 512-MiB repository smoke was OOM-killed, so the project lead authorized this modest repository increase; it is not represented as a successful 512-MiB run. CI and exported-image provenance must prove both task types at these exact limits in quota and guarded single-CPU modes. Measure actual cgroup enforcement, peak memory, cleanup and the collaboration service's response time with both a small trial and a repository dependency/edit/test task. The service's separate 512-MiB application cap is not the container capacity plan: size and verify the shared parent cgroup independently before changing the private host profile. A reduced-memory failure stays an explicit failure, without swap spill, silent resource expansion or replay. These test targets do not change general self-host defaults or resource ceilings.
5. Reconfirm current provider prices, account eligibility and third-party service terms. Then use the approved private API credential for a real tool-call round trip and a small multi-turn code-edit/test task on each configured model. The free-model template and fixture tests do not prove current zero pricing or compatibility. No paid fallback, permission broadening or automatic purchase is authorized.
6. With each prerequisite recorded, activate the corresponding test-only server switches, restart the reviewed test service and check current public model status, an approved user's task, failure/cooldown behavior and cleanup. A later production promotion remains separately authorized. Put secrets only into restricted configuration through the approved host procedure; never paste them into chat or commit them.

## Selected free-model setup

The first selected provider is SiliconFlow. On 2026-10-08, the complete expanded [official price page](https://siliconflow.cn/pricing) and [Model Square](https://cloud.siliconflow.cn/models) identified six current candidates with zero input/output prices and the provider's **Tools** capability: `Qwen/Qwen3.5-4B`, `Qwen/Qwen3-8B`, `Qwen/Qwen2.5-7B-Instruct`, `THUDM/GLM-4-9B-0414`, `THUDM/GLM-Z1-9B-0414`, and ChinaTelecom's `XingChenAGI/Xing4.0-29B`. The reviewed [full free-model inventory](HOSTED_AGENT_FREE_MODELS.md) separates these from free reasoning/specialist models and retired or paid variants. They are integration candidates, not provider-tested models. Copy the inactive [environment template](../ops/hosted-agent/siliconflow-free.env.example) into the private server configuration. Prepare an eligible verified account and `GATHERTHREAD_SILICONFLOW_API_KEY`; keep the key out of chat, source, browser storage and screenshots. Configure the reviewed image digest, reconfirm zero pricing and account terms, and run real tool-call/coding and deployment-host tests before activation.

`GATHERTHREAD_HOSTED_AGENT_PRESET=siliconflow-free` supplies the six reviewed candidates through the existing HTTPS Chat Completions adapter, retaining the original `sf-qwen35-4b` and `sf-qwen3-8b` identities and first default. Set `GATHERTHREAD_SILICONFLOW_FREE_MODELS` to a JSON array of exact catalog IDs to expose only models that passed the deployment's real compatibility checks; an empty list, duplicates, unknown/paid/Pro IDs or malformed JSON are rejected. Omission selects the full reviewed catalog, not an automatically discovered provider list. The subset applies only with this preset. All models share one account capacity group; adding models never creates extra account/host capacity. A preset and `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` cannot be combined. There is no paid fallback or silent model switch.

This preset has **no daily task-count allowance** for users or the deployment by default. Each user may run one task at a time, with at least 30 seconds between accepted starts; the general host/account default is two simultaneous tasks, but Beta 1 test activation starts with the private host limit set to **one**. The provider's own RPM/TPM limits, 429 cooldown, and the existing per-task tool-call, context, memory and timeout bounds still apply. These controls do not promise unlimited parallel capacity or a fixed inference speed. Browser settings reuse the existing model/status fields and omit “runs left today” when the user daily limit is absent.

The general provider setup retains `GATHERTHREAD_HOSTED_AGENT_USER_DAILY_RUNS` (default 1) and `GATHERTHREAD_HOSTED_AGENT_GLOBAL_DAILY_RUNS` (default 4). The explicit value `none` disables a default daily limit only when **all** endpoints are reviewed, confirmed zero-price SiliconFlow catalog models with `daily_runs: null`. Other providers/models retain numeric account and user/global ceilings. Explicit per-user administrator limits remain effective, including `hosted-agent:set-user-limit --user-id ID --runs 0` to deny one user. Remove old daily-run/Neuron environment overrides when switching to the free preset; administrator overrides remain effective. If prices or provider eligibility change, stop the free service and review configuration before accepting more tasks.

## Multiple APIs and accounts

Interactive trial requests to the reviewed SiliconFlow `Qwen/Qwen3.5-4B` and `Qwen/Qwen3-8B` profiles explicitly disable hidden thinking. SiliconFlow's `max_tokens` limits public answer tokens, not reasoning tokens; see its [Chat Completions contract](https://docs.siliconflow.cn/docs/api/chat-completions-post). This does not switch models or change other providers or local Codex/DSH settings. It is not evidence that a previously uninstrumented failure was caused by reasoning. The runner emits only fixed failure-stage categories, never raw harness, tool or provider output; a live same-image request is needed to establish actual compatibility and latency.

Example `GATHERTHREAD_HOSTED_AGENT_ENDPOINTS` value (put actual `DEEPSEEK_A` and `DEEPSEEK_B` secrets only in the private environment):

```json
[
  { "id": "ds-a", "profile_id": "coding", "label": "DeepSeek coding", "provider": "deepseek", "model": "deepseek-chat", "token_env": "DEEPSEEK_A", "quota_group": "account-a", "daily_runs": 20, "max_concurrent": 1 },
  { "id": "ds-b", "profile_id": "coding", "label": "DeepSeek coding", "provider": "deepseek", "model": "deepseek-chat", "token_env": "DEEPSEEK_B", "quota_group": "account-b", "daily_runs": 20, "max_concurrent": 1 }
]
```

Replace the example model with a model actually available on the accounts. Up to 32 endpoints may be configured. Entries under one `profile_id` must have the exact same provider, model and display label. A different provider/model needs its own profile and an explicit user selection. The scheduler reserves one available account with the fewest active runs, then the fewest daily reservations. There is no waiting queue or automatic provider/model fallback. If upstream returns 429, 401/403 or 5xx, that account enters a short in-memory cooldown for subsequent tasks; the accepted run is not replayed automatically on another account.

All keys belonging to the same billed account or organization **must use the same `quota_group`**, daily limit (including `null`) and concurrency limit. Shared groups count usage across models. Use only legitimately provisioned capacity in accordance with provider terms; multiple keys on one account do not create extra quota. Group IDs must stay stable across restarts/configuration changes or accounting cannot associate previous usage. The operator is responsible for mapping non-Cloudflare credentials to their real accounts. Browser status exposes only model choices, availability, user rate limits and any configured daily allowance, never account IDs, endpoints or secrets.

For a custom provider use `provider: "openai-compatible"`, `base_url: "https://api.example.com/v1"`, an explicit model and quota group. URLs must be HTTPS without embedded credentials or query parameters. Streaming tool-call compatibility must be tested with the real service.

Cloudflare entries use `provider: "cloudflare-workers-ai"`, `model: "@cf/qwen/qwen3-30b-a3b-fp8"`, `account_id`, `free_plan_confirmed: true`, and at most four daily runs. Their quota group is derived from the account ID, so multiple keys cannot multiply the account allowance. The legacy single-Cloudflare environment variables remain supported when no endpoint JSON is configured: `GATHERTHREAD_HOSTED_AGENT_FREE_PLAN_CONFIRMED`, `GATHERTHREAD_CLOUDFLARE_ACCOUNT_ID`, `GATHERTHREAD_CLOUDFLARE_AI_TOKEN`. Old `*_DAILY_NEURONS` values convert to whole runs by dividing by 2000; new run variables take precedence.

Every run reserves its user cooldown, user/account/host slot and any configured daily allowance transactionally before its canonical request is created. A failed accepted task still consumes its start interval and any daily allowance. Rejected requests consume neither a slot nor an interval; exact idempotent replay never consumes another reservation. Trial proxies cap eight calls, 64,000 bytes per request and 1024 output tokens per call; [repository tasks](HOSTED_GITHUB.md) have separate bounded allowances. Cloudflare additionally keeps the conservative 2000-Neuron per-run ceiling and cannot run repository tasks. Other providers use bounded runs, **not invoice-accurate token/currency accounting**: set a provider-side spend cap for paid models and monitor the actual bill. A successful idempotent replay never launches another container.

The container runs without general network access, host credentials, or writable host directories. Its working directory is a bounded in-memory filesystem; the host supplies only read-only initial code. It is non-root, read-only except for bounded temporary storage, and has CPU, memory, PID, and wall-time limits. A user's code can run terminal commands **inside that container**, so do not mount the Docker socket, server database, deployment files, SSH agent, or host home into it. OpenCode permissions are convenience controls inside the container and are not the isolation boundary.

The entrypoint starts one pinned `opencode serve` process on container loopback, creates a fresh session and awaits its completed prompt response. It validates the exact session, final finish, absence of an error and idle state, then shuts down the server and waits for closure before reading changed files. Only assistant text is shared; server logs, reasoning and tool results are excluded. A partial answer or failed process shutdown is never treated as a completed run. This path is part of the image, so deploy matching application and immutable image artifacts; Web-only updates cannot repair the executor. See [ADR-0041](adr/0041-guided-settings-and-ephemeral-hosted-startup.md).

## Current limits

The preview accepts at most 100 project files and 500 KiB of code, at most 12 KiB of shared conversation context, and a five-minute run. Each model request still has a 30-second deadline, with the existing eight-call and output caps. GitHub repository tasks retain their separately documented fifteen-minute limit. Package downloads and arbitrary web access are unavailable from the trial container. Commands using dependencies already present in the image or source workspace can run; a project that needs external packages must use a separately approved dependency strategy. New files that exceed the cloud code rules are not checkpointed. These limits keep the trial service bounded; they are not a claim that every project can build inside this runner.

The operator must validate the container path on its deployment host before enabling the flag. Unit tests use a mocked Docker runner and model response; they do not prove that OpenCode can complete a real provider-backed project task. No billable provider request is made by the test suite.

For provider alternatives and the exact operator handoff, see [model API options](HOSTED_AGENT_PROVIDERS.md).

## Upgrade compatibility

The free-profile status contract uses `null` for absent daily limits and adds optional `rate_limits` plus `user_busy` / `rate_limit` availability states. Deploy the matching server and Web assets together; earlier preview clients cannot interpret unlimited daily status. Numeric quotas keep their previous meaning, and administrator `--runs 0` still disables a user. The additive `hosted_agent_user_activity` and `hosted_agent_active_runs` tables backfill existing reservations idempotently, retain cooldown after session/project deletion and keep an active slot until completion or single-process startup recovery. User activity has one row per account, and active slots are bounded by host capacity. Account deletion removes user activity and nulls the active slot's user link; the minimal request ID, quota group and start time remain only until its executor settles. Completion releases the slot even when task, session or account rows no longer exist. A failed Docker exit check retains its slot until operator recovery; model sockets and temporary source are still cleaned. Startup stops and verifies all interrupted `gt-hosted-*` / `gt-repository-*` containers on the dedicated Docker host before releasing reservations; cleanup failure prevents startup. The atomic migration from cascading active slots preserves every extant reservation and its indexes. It cannot reconstruct slots already removed by an earlier preview. Downgrading this preview loses the new rate-control guarantees and requires stopping all runners first.

`hosted_agent_daily_usage` separately retains only the request ID, user ID, UTC day and quota group for each accepted reservation. It has no event/session/project/account foreign key: deleting cloud history, a saved task or an account does not refund that day's user/global/account consumption. Completed, failed and interrupted tasks count alike; exact retry does not create another charge. Startup atomically backfills retained current/legacy jobs with `INSERT OR IGNORE`; restarting or recovering interrupted slots leaves current-day charges intact. Startup and subsequent accepted reservations remove older UTC days. No deleted message body, source, device ID or provider credential is retained in this ledger. Reservations deleted before this migration cannot be reconstructed; the migration cannot recover their past usage. Downgrading to a preview that counts only retained jobs loses this guarantee and is unsupported.

Deploy server and Web assets together. The status response now advertises profiles and run counts instead of the earlier preview's single fixed model and Neuron counters. Old requests without `profile_id` use `default` only if that profile exists. Old accepted requests whose payload omitted the profile must not be silently reinterpreted; conflicting reuse returns 409. Browser settings v13 supports the cloud choice while preserving the active local harness and its settings. Beta 1 opens the Web entry, but neither settings defaults nor migration configure or enable the server runner.

Already accepted jobs can settle after their timeline fills or a storage cap is lowered. A model answer must still fit ordinary storage quotas; otherwise only a fixed charged failure is retained. The private terminal control allowance and confirmed-exit release rule are specified in [Security](SECURITY.md#persistence-and-redaction-requirements). Recovery never retries model execution automatically.

SQLite upgrade retains the original preview tables and copies existing reservations, IDs and user limits into `hosted_agent_runs` / `hosted_agent_run_limits` idempotently. Earlier reservations with no account metadata count conservatively against every account for that UTC day. Stop the old process and back up the database before upgrading. Downgrading to the old single-provider runner after accepting pooled runs would undercount usage and is unsupported; restore a pre-upgrade backup only with explicit data-loss review. This is a single active server-process design, not a distributed worker scheduler.
